# สำรองและกู้คืน D1

ใช้คู่มือนี้เพื่อสร้างไฟล์สำรองและตรวจว่ากู้คืนได้ ก่อนเปลี่ยน schema หรือดำเนินการที่ลบข้อมูลถาวร

## เตรียมเครื่องมือ

ติดตั้ง dependencies ด้วย `npm ci` และเตรียม Python 3 สำหรับตรวจฐานข้อมูล SQLite ใช้ Cloudflare API token ผ่าน environment หรือระบบจัดการ secrets ของหน่วยงาน ห้ามเขียน token ลง repository

คำสั่งที่มี `--remote` ติดต่อ Cloudflare จริง ส่วนการตรวจการกู้คืนในคู่มือนี้ใช้ D1 local แยกจากฐานข้อมูลพัฒนาเสมอ

## สร้างไฟล์สำรอง

ใช้การ export มาตรฐานเมื่อเข้าถึง Cloudflare และโดเมน storage สำหรับดาวน์โหลดไฟล์ได้:

```sh
npm run db:backup -- --remote
```

คำสั่งสร้างโฟลเดอร์ใหม่ใน `backups/` ทุกครั้ง ภายในมี `database.sql` และ `manifest.json` ซึ่งบันทึกเวลา ขนาดไฟล์ และ SHA-256 สิทธิ์โฟลเดอร์เป็น `0700` และไฟล์เป็น `0600` บนระบบที่รองรับ และ `backups/` ถูกละเว้นจาก Git

สำหรับฐานข้อมูล local ใช้ `npm run db:backup -- --local`

### ใช้ snapshot ผ่าน API เมื่อโดเมน storage ถูกบล็อก

สภาพแวดล้อมของโครงการอนุญาต `api.cloudflare.com` แต่บล็อกโดเมนดาวน์โหลด export บน R2 ใช้วิธีอ่านข้อมูลผ่าน D1 API โดยตรงได้:

```sh
npm run db:backup -- --remote --api-snapshot
```

วิธีนี้ต้องกำหนด `CLOUDFLARE_ACCOUNT_ID` และ `CLOUDFLARE_DATABASE_ID` ให้ตรงกับฐานข้อมูลเป้าหมาย นอกเหนือจาก `CLOUDFLARE_API_TOKEN`

ตัวสร้าง snapshot อ่าน schema ก่อน แล้วอ่านข้อมูลทุกตารางใน SQL SELECT เดียวเพื่อให้ได้ข้อมูล ณ snapshot เดียวกัน ตรวจว่า schema ไม่เปลี่ยนระหว่างอ่าน และสร้างไฟล์ SQL พร้อมดัชนีและค่าลำดับอัตโนมัติ วิธีนี้รองรับเฉพาะ 7 ตารางของ BS-SAMS ปัจจุบัน หาก schema เปลี่ยนจะหยุดให้ตรวจสอบก่อน

ข้อความขนาดใหญ่ เช่น JSON ที่มีโลโก้ จะแบ่งเป็นคำสั่ง UPDATE ย่อย เพื่อให้แต่ละคำสั่งไม่เกิน 90,000 ไบต์ ข้อมูลภาษาไทย เครื่องหมายคำพูด และบรรทัดใหม่ยังคงเดิม หากเกินขีดจำกัดผลลัพธ์หรือเวลาของ D1 API ให้ใช้ native export จากเครือข่ายที่เข้าถึงโดเมน storage ได้

## ตรวจว่าไฟล์กู้คืนได้

ใช้ path ที่คำสั่งสำรองแสดง:

```sh
npm run db:verify-recovery -- --snapshot backups/<timestamp>/database.sql
```

คำสั่งตรวจ SHA-256 ก่อนอ่านฐานข้อมูล จากนั้นนำเข้าไฟล์ด้วย Wrangler ลง D1 local ชั่วคราว และตรวจ:

- โครงสร้างตาราง ดัชนี และข้อมูลทุกแถวตรงกับไฟล์สำรอง
- ค่าลำดับอัตโนมัติของ SQLite ตรงกัน
- `PRAGMA integrity_check` ผ่าน และไม่พบข้อผิดพลาดจาก `foreign_key_check`
- ลบ session หลังการกู้คืนแล้วเหลือศูนย์ เพื่อยืนยันขั้นตอนเพิกถอนการเข้าสู่ระบบ

ผลอยู่ใน `verification.json` ข้างไฟล์ SQL ประกอบด้วย fingerprint จำนวนแถว และเวลาทดสอบ ไม่มีรายละเอียดบุคคลหรือรหัสผ่าน ฐานข้อมูลทดสอบจะถูกลบทิ้งเมื่อจบ

เลือกใช้ไฟล์ที่มีผล verification ผ่านเท่านั้น การ export สำเร็จเพียงอย่างเดียวไม่ยืนยันว่ากู้คืนได้ การตรวจนี้พิสูจน์การนำเข้าบน D1 local ไม่ได้ย้อนข้อมูลใน D1 จริง และไม่ได้ทดสอบคำสั่ง Time Travel restore บนระบบใช้งานจริง

## กู้คืนเมื่อเกิดเหตุจริง

1. ระงับการบันทึกข้อมูลระหว่างจัดการเหตุ และสร้าง snapshot สถานะปัจจุบันอีกชุดเพื่อเก็บข้อมูลหลังเวลาของ backup
2. ตรวจ `manifest.json` และรัน `db:verify-recovery` กับไฟล์ที่เลือก
3. เตรียม D1 สำหรับกู้คืนแยกต่างหาก ตรวจชื่อและ database ID ก่อนใช้คำสั่ง remote
4. นำเข้า SQL ลงฐานข้อมูลสำหรับกู้คืน ตรวจ schema จำนวนแถว และตัวอย่างรายงานให้ตรงกับ backup
5. รัน `DELETE FROM sessions;` ในฐานข้อมูลที่กู้คืน เพื่อไม่ให้ session จากอดีตกลับมาใช้งานได้
6. เปลี่ยน binding `DB` ให้ชี้ฐานข้อมูลที่ตรวจแล้ว จากนั้น deploy และทดสอบเข้าสู่ระบบ ทะเบียน และรายงานก่อนเปิดให้บันทึกข้อมูล

ไม่ควรนำเข้า SQL ทับ D1 ที่แอปกำลังใช้งาน ขั้นตอนเปลี่ยนฐานข้อมูลและ deploy ต้องทำโดยผู้ดูแลที่รับผิดชอบเหตุ การกู้คืนทั้งฐานข้อมูลอาจทำให้การแก้ไขหลังเวลาของ backup หายไป ต้องแยกข้อมูลส่วนนั้นไว้พิจารณาก่อนเปิดใช้งาน

## Time Travel และการเก็บสำรอง

เมื่อสำรอง remote สคริปต์จะพยายามบันทึกข้อมูล Time Travel ปัจจุบันไว้ใน manifest ด้วย Bookmark นี้อ่านหลังการ export จึงไม่ใช่หลักฐานว่าเป็น snapshot เวลาเดียวกับไฟล์ SQL

ช่วงเวลาที่กู้คืนย้อนหลังได้ขึ้นกับแผน Cloudflare ให้ตรวจ D1 dashboard ของบัญชีจริงก่อนวางนโยบายเก็บข้อมูล งานนี้ตรวจว่าอ่าน bookmark ได้ แต่ไม่ได้เปลี่ยนแผนหรือกำหนดอายุ Time Travel

ไฟล์ SQL มีข้อมูลบุคคล password hash และ session ของระบบ เก็บในที่จัดเก็บถาวรที่จำกัดสิทธิ์และเข้ารหัสของหน่วยงาน อย่าพึ่งอายุ workspace หรือ Git เป็นที่เก็บสำรอง ระบุผู้รับผิดชอบ รอบสำรอง และอายุเก็บตามนโยบายหน่วยงาน พร้อมทดสอบกู้คืนเป็นระยะ

โครงการยังไม่ได้ตั้ง scheduler สำหรับสำรองไฟล์ SQL อัตโนมัติ คำสั่งนี้เหมาะสำหรับรันก่อน migration หรือเหตุที่ต้องมีจุดกู้คืน และใช้ต่อกับระบบงานตามเวลาของหน่วยงานได้
