# วัดประสิทธิภาพด้วยข้อมูลจำลอง

## รันการวัดซ้ำ

ใช้ Node.js 24 ขึ้นไป Chromium ที่ `/usr/bin/chromium` และ Poppler ที่มี `pdfinfo` กับ `pdftotext` รัน `npm ci` และ `npm run build` ก่อน:

```sh
npm run test:performance
```

ค่าเริ่มต้นทดสอบ 1,000 และ 10,000 ราย โดยส่งออก CSV และ EXCEL ครบทุกคน แต่จำกัด PDF ทะเบียนที่ 1,000 รายต่อชุด เพื่อให้รอบตรวจทั่วไปใช้เวลาและหน่วยความจำไม่มาก

ทดสอบ PDF ครบ 10,000 รายได้ด้วย:

```sh
npm run test:performance -- --sizes 10000 --pdf-rows 10000 --output-dir /tmp/bs-sams-performance-fullpdf
```

กำหนด `--samples` เพื่อเปลี่ยนจำนวนตัวอย่างเวลา API ได้ ค่าเริ่มต้นคือ 5 รองรับ 3–20 ตัวอย่าง `--sizes` รองรับ 100–100,000 รายต่อชุด และ `--pdf-rows` รองรับไม่เกิน 10,000 ราย ค่าที่รับได้เป็นขอบเขตของเครื่องมือ ไม่ใช่การรับรองว่าแอปรองรับทุกขนาดนั้น

ผล JSON ไฟล์ส่งออก และภาพรายงานอยู่ใน `--output-dir` ค่าเริ่มต้นคือ `/tmp/bs-sams-performance` สคริปต์สร้าง D1 และ Worker แยก ใช้ข้อมูลจำลองเท่านั้น และลบฐานข้อมูลชั่วคราวเมื่อจบ ไม่แก้ไข D1 พัฒนาหรือระบบจริง

## สิ่งที่ตรวจ

แต่ละคนมีคำขอ 2 รายการ และการช่วยเหลือ 1 ครั้ง อีก 5% ของจำนวนคนถูกเพิ่มเป็นรายการในถังขยะเพื่อตรวจว่าไม่ปนกับรายงาน ผู้ใช้ทดสอบเป็นผู้ดูแลที่สร้างเฉพาะใน fixture

- API ทะเบียนหน้าแรก หน้าท้าย และตัวกรองสถานะ ประเภท และข้อความค้นหา
- API รายงานสรุปและส่งออกรายงาน พร้อมตรวจจำนวนคน คำขอ ผู้ได้รับการช่วยเหลือ และยอดเงิน
- คำขอรายงานพร้อมกัน 5 ชุด
- เวลาเปิดภาพรวมและทะเบียนใน Chromium
- CSV และ EXCEL ครบทุกหน้าพร้อมตรวจจำนวนแถว
- PDF ทะเบียนตามตัวกรอง พร้อมตรวจจำนวนบุคคลไม่ซ้ำในข้อความ PDF และ PDF รายเดือน
- ข้อผิดพลาด JavaScript และค่าสูงสุดของ JS heap ที่สุ่มอ่านระหว่างทดสอบ

ตัววัดเป็นเวลาตั้งแต่ส่งคำขอจนอ่าน response ครบ หรือคลิกจนดาวน์โหลดเสร็จ เวลา API ไม่มีเวลาสร้างไฟล์ในเบราว์เซอร์รวมอยู่ด้วย

## ผลที่ตรวจเมื่อ 31 ตุลาคม 2569

วัดกับแอป commit `d733f03` ใน local Worker/D1 และ Chromium บนเครื่องทดสอบ หน่วยเวลาเป็นมิลลิวินาที ค่า P95 ของตัวอย่างเพียง 5 ครั้งเท่ากับค่าสูงสุดของชุดนี้ ไม่ใช่สถิติระยะยาวของระบบจริง

| รายการ                       | 1,000 ราย | 10,000 ราย |
| ---------------------------- | --------: | ---------: |
| API ทะเบียนหน้าแรก P95       |        13 |         14 |
| API ทะเบียนหน้าท้าย P95      |        10 |         14 |
| API ทะเบียนพร้อมตัวกรอง P95  |        22 |        136 |
| API รายงานสรุป P95           |        49 |        301 |
| API ส่งออกรายงาน P95         |        51 |        229 |
| รายงานพร้อมกัน 5 ชุด เวลารวม |       122 |      1,157 |
| เปิดทะเบียนในเบราว์เซอร์     |       158 |        108 |
| ดาวน์โหลด CSV ครบทุกคน       |       137 |        449 |
| ดาวน์โหลด EXCEL ครบทุกคน     |       423 |      1,236 |
| PDF ทะเบียนครบทุกคน          |     1,233 |      5,833 |

PDF 1,000 รายมี 34 หน้า ส่วน PDF 10,000 รายมี 334 หน้าและขนาดประมาณ 2.1 MB PDF รายเดือนสำหรับชุด 10,000 รายใช้ 340 ms และมี 1 หน้า JS heap สูงสุดที่สุ่มอ่านได้ในรอบ PDF 10,000 รายอยู่ที่ประมาณ 194 MiB ไม่พบ page error และยอดรวมรายงานตรงกับข้อมูลจำลอง

เกณฑ์ตรวจรอบนี้คือทะเบียนหน้าแรก P95 ไม่เกิน 500 ms รายงานสรุป P95 ไม่เกิน 2,000 ms และ PDF ทะเบียนไม่เกิน 30 วินาที ทั้งสองขนาดผ่านเกณฑ์ เวลาต่างกันได้ตามเครื่อง cache และภาระงาน ไม่ควรใช้ตัวเลขเหล่านี้รับรอง SLA บน Cloudflare

## ขอบเขตที่ยังไม่ได้พิสูจน์

ยังไม่ได้ทดสอบข้อมูลเกิน 10,000 ราย อุปกรณ์มือถือหน่วยความจำน้อย หรือภาระงานพร้อมกันเกิน 5 รายงาน และยังไม่ได้วัด latency หรือ CPU limit ของ Worker บน Cloudflare จริง

รายงานยังอ่าน JSON ของบุคคลทั้งชุดที่ตรงสิทธิ์แล้วคำนวณใน Worker การค้นหาแบบข้อความและสถานะต้องตรวจ JSON ของหลายแถว จึงโตตามจำนวนข้อมูล หากข้อมูลหรือผู้ใช้เพิ่มขึ้น ให้ทดสอบขนาดใช้งานจริงก่อน และพิจารณา SQL aggregation หรือ schema คำขอแยกตารางเมื่อเกินเกณฑ์

PDF จำนวนมากใช้หน่วยความจำในเบราว์เซอร์มากกว่าการเปิดทะเบียน สำหรับมือถือควรกรองข้อมูลให้เล็กลง หรือส่งออก CSV/EXCEL และใช้ PDF รายบุคคลเมื่อเหมาะกับงาน
